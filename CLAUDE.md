# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal "calendar agent". It reads university (IIITH) emails that have been forwarded to a personal Gmail account and turns deadlines, meetings and events into Google Calendar events and Google Tasks. Everything runs locally; a local Ollama model (`gemma2:9b`) does the text extraction. Timezone is always `Asia/Kolkata`.

**Why Gmail:** the IIITH Outlook tenant blocks Microsoft Graph (it needs admin consent). `test_graph.py` is the leftover failed Graph attempt. Instead, a Power Automate flow forwards every IIITH email to Gmail, so messages arrive **from the user's own IIITH address** with an `FW:` subject prefix. The real sender and date are only in the body. Calendar invites arrive as `.ics` attachments.

## Build is phased — stop after each phase

The user wants the project built in phases and tests each one before the next starts. Finish a phase, tell the user exactly what to run and what they should see, then stop.

- **Phase 0 (done):** OAuth (`auth.py`), `config.yaml` / `config.py`, `test_gmail.py`, `list_calendars.py`.
- **Phase 1 (done):** `ingest.py`. See the pipeline notes under Architecture.
- **Phase 2 (done):** units in `systemd/` (copied to `~/.config/systemd/user/`): `calendar-ingest.timer` every 30 min, `calendar-approvals.service` always on, `calendar-digest.timer` at 07:00. `digest.py` delivers via `notifiers.CHANNELS` (desktop, telegram) and writes `logs/digest.md`.
- **Phase 3 (done):** `planner.py` + `slots.py` (pure interval math) + `ranker.py` (LLM ranks only, fallback earliest-due) + `llm.py` (shared guarded Ollama call). `calendar-planner.timer` runs `planner.py --auto` every 15 min + at login; `--auto` is a no-op before `planner.plan_after` or once `state.plans` has today. Habits in `config.yaml` `habits:` (empty by default).

Keep one file per responsibility. Update the file table in `README.md` whenever a file is added. Ask before anything destructive, including deleting the duplicate `client_secret_*.json` files or `temp/`.

## Architecture

- Every script gets Google access through `auth.get_credentials()` and settings through `config.load_config()`, then calls `googleapiclient.discovery.build(...)` itself. Don't duplicate OAuth or YAML loading in new scripts.
- `auth.SCOPES` is the single scope list: `gmail.readonly`, `calendar`, `tasks`. If a new feature needs another scope, add it there. `get_credentials()` notices when the saved token lacks a scope and re-runs the browser flow; it also re-runs it when refresh fails.
- `config.yaml` holds:
  - `gmail_query`: default `label:iiith`; the fallback is `subject:FW from:<iiith address>`.
  - `timezone`.
  - `calendars.{college, planner, habits}`: Google Calendar IDs (filled in).
  - `ollama.{model, num_ctx, num_thread, keep_alive, min_free_ram_gb, timeout_s, require_gpu}`, `min_confidence`, `first_run_days`, `tasklist` (the agent's own "College" list), `approval`, `skip_senders`, `keywords`.

### Ingest pipeline (`ingest.py`)
`gmail_reader.fetch_messages` → per message: `state` checks → `ics_import.parse_ics` (if an `.ics` is attached) **or** `extractor.matches_keywords` + `extractor.extract_items` → `google_writer.create_event` / `create_task` → `state.record_item`.

- **The LLM never does date math.** It copies date/time words verbatim (`date`, `start_time`, `end_time` fields); `dates.resolve_date` / `resolve_time` turn them into values. This replaced a `start`/`end` ISO schema after gemma2:9b repeatedly resolved "next Friday" to the wrong day. The prompt gives only the received *date*, no time, because the model copied the received time into items.
- **Three dedupe layers:** Gmail message ID → content fingerprint → normalised title + start (`ingest.dedupe_key`). The fingerprint exists because each email arrives twice via two forwarders, with different forward headers (`Sent:` in IST vs UTC). `gmail_reader.split_forward_header` removes that block before hashing, and also extracts the original sender for the prompt.
- **Items are plain dicts:** `type, title, start, end, all_day, due, course, location, description, recurrence`. `start`/`end` are aware datetimes, or `date` objects when `all_day`. A deadline is stored as a 30-min event ending at `due`.
- **`--dry-run`** runs Gmail and Ollama for real but uses an in-memory copy of `state.db` (`State(dry_run=True)`). Nothing is written to Google or disk except `logs/ingest.log`.
- **Failure handling:** `LLMUnavailable` or any exception leaves the message unprocessed so the next run retries it; `last_run` only advances on an error-free run. Invalid JSON from the model is outcome `unreadable` (listed in `/skipped`; at temperature 0 a retry would fail the same way). A `TelegramError` from `approvals.ask` with "network error" is not counted against the email and stops the loop (no model time spent on items that can't be asked about); other Telegram errors are counted. `check_mail_flow` alerts (`no-mail`) when no IIITH mail at all was listed for 3 days.
- **Filters before the LLM:** `skip_senders` (fnmatch against `msg["from_line"]`, the raw forwarded `From:` line including the mailing list; `life@lists.iiit.ac.in` = clubs) → `skip_subjects` (substring; Slides share notices come from people's own addresses, so a sender rule can't catch them) → fingerprint (NFKC + curly quotes/dashes folded: the two forwarders disagree on typography) → `extractor.matches_keywords(text, keywords, weak_keywords)`: a strong keyword anywhere (each word may take a plural and hyphen/space variants: "mid sem" matches "Mid-sem", "midsem"), or a weak keyword plus a concrete day in the same sentence, or "till/until/by/before <day>". A pure keyword list dropped 20 of 54 real emails, including a real deadline. Skipped emails keep their subject (`processed_messages.subject`, outcome `no-keyword`, or `unreadable` for invalid model JSON via `extractor.UnreadableAnswer`) for `/skipped`; its Read button runs `ingest.py --message <id>` (`read_one`: bypasses filter and fingerprint). `msg["sender"]` is the real person after "On Behalf Of"; the sender "unknown" is never offered for blocking.
- **Resource guards in `llm.chat_json`:** refuses when `MemAvailable` < `ollama.min_free_ram_gb`. GPU: if the model is loaded with less than `MIN_GPU_SHARE` (30%) in VRAM (before the call, or seen after it), it unloads, alerts, and stores `meta llm_cpu_only_since`; for `GPU_RETRY_AFTER` (6 h) every call is refused without touching Ollama (power-saver mode / Ollama without CUDA would otherwise mean a hot CPU inference every run). `/check` clears the flag. Normal split is ~71% GPU / 29% CPU. Refusals raise `LLMUnavailable` (email retried next run, not counted; `meta llm_waiting` counts them for `/status`). A timeout raises `LLMTimeout`, which *is* counted against the email. `num_predict` is capped at 700.
- **Approval flow (`approval.enabled`):** `ingest.py` does not create items. It calls `approvals.ask()`, which inserts a `pending_items` row (the item is JSON via `state.item_to_json`), then sends a Telegram card with `add:<id>` / `skip:<id>` buttons (if the send fails, the row is deleted so the next run retries). `approvals.py` is a separate long-polling process that handles taps: it checks the chat id, calls `google_writer.create_item`, and records in `created_items`. Dedupe covers both tables (`item_exists` or `pending_exists`). Only `approvals.py` may call `getUpdates`: Telegram allows one consumer at a time. `telegram_bot.TelegramError` messages never include the token.
- **Pause:** `/pause` / `/resume` / `/status` are handled in `approvals.Listener.handle_message` (owner chat only). The flag is `meta.paused_since` in `state.db`. `ingest.py` skips Gmail while paused (the calendar watch still runs), and `last_run` doesn't advance, so resuming catches up. `/resume` starts `calendar-ingest.service` immediately. The listener now receives both `callback_query` and `message` updates.
- **Digest:** "Deadlines" = `DUE:` events on the college calendar (their *end* is the due time). A deadline counts as planned if a planner event before it has `extendedProperties.private.deadline_event_id` equal to the DUE event's id, or its title contains the deadline title. Phase 3 must set `deadline_event_id` on work blocks. Tasks from the agent's own `tasklist` are left out because they duplicate the DUE events. `build_digest` is testable offline by monkeypatching `fetch_events`, `fetch_tasks`, `get_credentials`, `build` and `State`.
- **Morning flow (`morning.py`):** `calendar-morning.timer` (every 15 min + at login) runs `--tick`. Once a day after `plan_after` it sends the check-in, then calls `finish()` on Done (listener → `systemd-run morning.py --finish`) or after `morning.wait_minutes`. `finish()` = `planner.plan_today` + `digest.build_digest(skip_planner_blocks=True)` merged into one message. State lives in `meta` keys `checkin_sent_at`, `checkin_done`, `morning_sent` (set only once **Telegram** has the message; a desktop-only delivery stores the text in `morning_pending` and `_retry_telegram` resends just that on later ticks, without re-planning) and `morning_in_progress`. Check-in buttons are dated (`checkin:done:<date>`, `morning.checkin_buttons`); a stale one is refused. Typed done/nothing words (`approvals.DONE_WORDS` / `NONE_WORDS`) act as the buttons. After `morning.latest_checkin` (18:00) there's no check-in, only the plan with a late-start note. A non-network planner failure still sends the digest with the reason. The first tick each day backs up `state.db` to `backups/` (7 kept). Plain Telegram text is a to-do only while `morning.checkin_open()` is true; otherwise `/todo`. `todos.add` stores each to-do's minutes as effort under `task:<id>`, so the planner gives it exactly that time. The old `calendar-planner.timer` / `calendar-digest.timer` are superseded (disabled on this machine).
- **Slot picking (`slotpicker.py`):** the morning (`morning.finish` → `slotpicker.prepare` + `morning_lines`, then `followups` → `send_waiting`) and `/plan` (`planner.suggest`) never book anything: each task needing time today gets a `plan_items` row and its own message with free slots (`slotpicker.options`: spread morning/afternoon/evening, before `due - gap`) as `sgb:<item>:<HHMM>:<min>` buttons, plus `sgm` (more) / `sgn` (not today; moves a to-do's due date). Booking re-checks the slot against a fresh `planner.work_context`, creates the block, records it in `booked_blocks` and redraws the other open messages. `slotpicker.tick` (from `morning.tick` every 15 min, not during sleep): "Did you finish?" (`bkd:<block>:<d|p|x>`) for ended booked blocks, one reminder per task (`remind_after_minutes`, counted from `sent_at`), the evening check (`eve:`) once a day. Answers weight done work in `planner.block_minutes` (`DONE_WEIGHT`; unanswered = 100%). `planner.work_context` is the shared "free time + need today" function (`need` = today's share minus booked). Exams: `planner.exam_kind` on College event titles; prep = `exam_prep_hours` by kind, overridable per exam (`efforts` row `event:<id>`, 0 = no prep; `/exams`, `prep:` buttons). `--place` / `--auto` keep the old automatic placement.
- **Shared plan changes (`actions.py`):** move/book/skip/busy/finish/drop go through here from the bot (`slotpicker`,
  `deadlines`, `nlcommands`) and the web page, so the same checks apply: `free_on(day)` (= `planner.free_today` with a
  synthetic now) and `fits`; a clash returns `nearest_free` alternatives. Blocks keep their calendar in
  `booked_blocks.calendar` (habits calendar for habits). Busy time is a planner-calendar block with kind `busy`.
- **Typed changes (`nlcommands.py`):** `parse_rules` (ordered regexes) then `parse_llm` (JSON intent with copied time
  words, guarded by `llm.chat_json`); `find` fuzzy-matches the task among `targets` (booked blocks, today's items,
  deadlines/exams, habits); `propose` returns a question + proposal stored in `meta nl:<n>`; `nl:y|n|t` taps apply it
  via actions. Plain text outside the check-in and outside a waiting conversation goes here before the help text.
- **Conversations:** a button that asks you to type (a setting value, a habit's name, a due date) stores
  `meta conv` via `state.set_conv(now, flow, ...)` (15 min); `Listener.handle_message` routes the next plain message to
  `settings.typed` / `habits.typed` / `deadlines.typed`.
- **Settings:** `settings.SETTINGS` is the registry (kind, choices, limits); values live in the `settings` table and
  `config.load_config()` lays them over config.yaml (`state.read_settings`, read-only). After changing one the listener
  reloads `self.cfg`.
- **Habits:** `habits` table (config.yaml habits imported once, `meta habits_imported`); `habits.today_items` feeds
  `planner.work_context` (habits first, key `habit:<id>`, `window_start`, due = window end); `_pick` limits each item
  to its window (`window_free`). Streak = scheduled days in a row with a Done block.
- **Heads-up:** the listener loop calls `slotpicker.heads_up` every minute (`booked_blocks.headsup` marks it sent);
  `hu:<block>:<s|p|k>`, `mvb:<block>:<YYYYMMDDHHMM>`.
- **Email moves/cancellations (`changes.py`):** `ingest.changes_in` runs before new items are asked about: same UID
  (invites; events carry `extendedProperties.private.ics_uid`), `same_thing` titles (difflib >= 0.8, numbers equal)
  at another time -> `ask_change` (`mv:`), cancellation words -> `ask_cancel` (`cx:`). These cards store sender None
  so skipping them never teaches sender blocking.
- **Web (`web/app.py`):** `create_app(services, state_factory, config)` (injectable for tests); single-threaded server
  on 127.0.0.1:8765 (Google clients aren't thread-safe); `guard()` checks Host allow-list, optional
  `Tailscale-User-Login`, Origin and the per-start CSRF token on every POST; strict CSP (no inline script/style: the
  JS sets positions through CSSOM). Event times are converted to the agent's timezone before they reach the page.
- **Planner invariants:** never let the LLM do time math: effort, done-hours, days-left and slots are all Python. Planner events are tagged `extendedProperties.private` `{source: calendar-agent-planner, plan_date, kind: habit|work, work_key, deadline_event_id}`; only tagged events are ever deleted (`google_writer.list_blocks` filters by `privateExtendedProperty`). `work_key` is `event:<DUE event id>` or `task:<task id>`; efforts from the Telegram buttons live in `state.efforts` under the same key. Done work = past tagged blocks with that `work_key`. `DUE:` events are created `transparent` and excluded from busy time.
- **Telegram commands** run work out of process: `/check` → `systemctl --user start calendar-ingest`; `/plan` (`calendar-plan-now`), `/clear` (`calendar-clear-now`), Done (`calendar-morning-now`), Read (`calendar-read-<id>`) → `systemd-run --user` transient units (so restarting the listener can't kill them). `_run_script` returns `True` / `"busy"` / `False`; busy is reported, never claimed as started. Done tapped while a plan runs sets `meta replan_requested`, and `planner.main` plans once more. Button-bar labels map to commands via `approvals.LABELS`.
- **One answer per tap:** Telegram shows only the first `answerCallbackQuery`. `approvals.Tap` answers once; actions in `SLOW_ACTIONS` (anything calling Google) are answered at the start, in a pre-pass over each update batch, and report results by editing their message; fast ones answer with a toast. Handler exceptions go to `Listener.report_error` (a reply, rate-limited; auth errors also alert). `Telegram.send` splits text over 4000 chars; `Telegram.edit` returns False instead of raising when the message was deleted; 429 is retried once after `retry_after`.
- **Unattended operation (Phase 4):** `auth.get_credentials()` never opens a browser without a TTY and raises `AuthExpired` instead (it loads `token.json` with its stored scopes, so a token missing a scope is noticed). Every entry script's `main` is wrapped in `@alerts.guard(name)`, which turns `AuthExpired`/`RefreshError` into one `alerts.alert("auth", ...)`, network errors (`alerts.is_offline_error`: TransportError, httplib2, requests, gaierror, HttpError 429/5xx, Telegram "network error") into one log line and exit 0 (alert `offline` only after 6 h), and other crashes into `crash:<name>` alerts (reset after a success). `alerts.alert(key, ...)` is rate-limited per key via `meta alert:<key>`, and `alerts.resolved` resets it. Ingest gives up on an email after `ingest.MAX_TRIES` real errors (`failures` table); `LLMUnavailable` doesn't count. `morning.finish` sets `morning_sent` only after `deliver()` succeeds, guarded by `morning_in_progress`. `planner.plan_today` holds an `fcntl` lock. Listener background runs use fixed systemd-run unit names (`calendar-plan-now`, `calendar-morning-now`).
- **Dates:** a same-day bare weekday means today, "next <weekday>" on the same day means +7 (time words are stripped first, so "next Friday 5pm" too), weekday words must match whole, "in N weeks" and "end of (next) month" are handled. The dateutil fallback only parses a matched real date (day + month name, or d/m[/y]); stray numbers ("Week 7", "Quiz 1") never become dates, and only dates more than ~6 months back roll to next year. `resolve_time_range` needs a real clock token (`10 AM`, `9:30`, `1700 hrs`, ranges like `2-4 PM`); otherwise None, so a deadline is due at 23:59, never 00:00. A deadline's due time is its `end_time` when given (submission windows). The reference date for relative words is the original `Sent:` time from the forward header (`gmail_reader.parse_sent`, stored as `msg["reference"]`), falling back to the Gmail arrival time.
- **Calendar watch (`calwatch.py`):** `ingest.watch_calendars()` runs a `Watcher` after the mail loop. Policies per calendar come from `load_calendars()`: the agent's own are `internal`; others read `meta calpolicy:<key>` (bot overrides) → `config.calendar_watch.calendars` → `default`. The primary calendar's key is `"primary"`, so the user's address is never written to config. State lives in `watched_events` (one row per event, or per series via `recurringEventId`). Statuses are `pending / tracked / ignored / deadline / linked / gone / expired`. `counts_as_busy()` (used by the planner) treats unanswered events as busy; `shown_today()` (used by the digest) lists only undecided ones, because tracked ones show through their College copy (tagged `mirror_of`). `run()` picks each series' next occurrence that hasn't *started* (an in-progress one used to make `_expire` drop an unanswered series); `_expire` skips series, which expire only when `series_ended()` (RRULE UNTIL/COUNT) says so. `_sync` compares `core()` for single events and `series_core()` (the most common time/length/title/place across the window's occurrences) for series, so one moved class isn't a series change. Tracked series are copied **per occurrence** for the next `days_ahead` days (`series_copies` table, `_sync_copies`: create new, patch moved, delete after missing twice; past copies stay as history); an old-style single repeating copy (`copy_id` on a series row) is ended at now with `google_writer.end_series_copy` and replaced. `_check_gone` needs a row missing on **two scans in a row** (`snapshot.missing`) before it acts, stores `before_gone`, and `_revive` restores a gone row whose event reappears. Rows of calendars switched to show/ignore keep being synced if tracked/deadline. Status writes that race with taps use `state.watch_set_if`. `track` / `ignore` / `as_deadline` re-read the row and clean up what an earlier decision made (no duplicate copies on double taps, no orphans when switching); Track/Ignore on a card act on `_card_rows` (that card's rows), not every same-title series. A failed card send leaves rows flagged for the review (or resent by `_requeue_unsent`). One scan at a time: `calwatch.watch_lock` (ingest skips if busy; `daily_review` waits, raising `WatchBusy` on timeout). `daily_review` sends first and only then marks rows, and edits the previous review after. Undo records carry `after` (and `policy_after`) and only restore rows still in that state; a second Undo tap changes nothing. Series with the same title on one calendar are one question (`group_rows` / `siblings`). **Daily review** (`calendar_watch.daily_review`): `Watcher.review_mode` queues non-urgent findings in `watched_events.review` (`new` / `changed` / `cancelled` / `copied`) instead of sending cards; `urgent_hours` bypasses this. `morning.maybe_review` (once per day, before the check-in; `meta calendar_review_sent`) calls `calwatch.daily_review`, which scans, then sends one message. Its items are stored in `meta review:<n>`, and `render_review` redraws it from row state. Buttons: `crv:<t|i|k|r|d>:<row>` and `crva:<t|i|o>:<n>` → `handle_review`. Changes to decided rows go through `Watcher._changed` (ask again) and cancellations through `_cancelled`. Every tap is answered immediately in `approvals.Listener.handle` (before the slow Google calls; late answers used to fail and let taps queue up), so `Telegram.answer` ignores errors. Calendar-wide changes go through `_confirm` → `calc:` and store an undo record (`meta calundo:<n>`: the previous policy override plus each row's previous status/copy); `calu:<n>` restores them and `_rerender` redraws each affected message once. **Never display a calendar's raw summary**: subscribed feeds are named after their URL, and the Moodle one contains an authtoken. Always go through `calwatch.label()`.
- **Offline checks:** `dates.py` and `extractor.validate()` are pure functions, and `ics_import.parse_ics` takes raw bytes. Test them directly with made-up input; no network or LLM needed.
